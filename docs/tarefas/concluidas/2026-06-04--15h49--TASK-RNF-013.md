## Decisões Tomadas

- **Validar presets na fronteira de build:** `repositorioPresets.ts` parseia cada JSON no `import.meta.glob`, porque preset inválido deve quebrar teste/build em vez de degradar silenciosamente.
- **Schema regional de subconjunto:** `dados_rj.json` contém metadados e combustíveis fora de `DadosRJ`; o contrato desta tarefa valida apenas o que o cálculo consome.
- **Strip default dos campos `_`:** campos de documentação dos presets (`_fonte`, `_notaServicosManutencao`, `_servicosSemPecas`) não entram no tipo runtime.
- **`PresetMotoCatalogo` como interface:** troca puramente tipológica para alinhar o tipo público ao objeto inferido pelo Zod sem enfraquecer o contrato.

## O Que NÃO Foi Feito (e Por Quê)

- **Não modelar o JSON regional inteiro:** fora do contrato `DadosRJ`; modelar tudo criaria tipo maior que o consumo real.
- **Não usar `.passthrough()` nos presets:** preservaria campos de documentação no runtime e quebraria a igualdade com `PresetMoto`.
- **Não criar schema duplicado para `ServicoIndependente`:** o schema existente em `perfilSchema.ts` agora é compartilhado.
- **Não adicionar dependências:** `zod` já era dependência de produção.

### 🟢 Sugestão
- `tabelaFipe: z.record(z.string(), numeroFinito)` aceita `0`/negativo; FIPE é sempre positivo — `numeroPositivo` seria mais estrito (baixo impacto; é fallback offline).

## Aprendizados Para o Projeto

- Zod com strip default funciona bem para JSONs que carregam documentação embutida, desde que o contrato runtime seja deliberadamente menor.
- Tipos por interseção podem atrapalhar `expectTypeOf().toEqualTypeOf()` mesmo quando a assignabilidade está correta; `interface extends` é mais legível para contratos expandidos.
- A fronteira certa para dado estático de build é o repositório de dados, não cada consumidor.
