## Decisões Tomadas

- **Ordem das refatorações:** TASK-REF-03 antes de TASK-REF-01 e TASK-REF-02, porque a camada `src/components/ui/` desbloqueia a componentização das páginas.
- **Migração completa de tokens em vez de camada de ponte (bridge):** análise de impacto mostrou 7 substituições globais mecânicas sem ambiguidade em 21 arquivos. Para projeto pequeno em fase inicial, a bridge acumularia dívida técnica a cada novo componente shadcn. Migração completa é mais limpa. Aprovação humana explícita recebida.
- **`components.json` criado manualmente em vez de `shadcn init`:** o CLI `init` sobrescreveria `index.css` com tokens HSL, conflitando com os tokens RGB do projeto. O comando `add` (sem `init`) aplica apenas os componentes e dependências necessários, sem tocar no CSS.
- **Componentes shadcn preferidos; próprios apenas sem equivalente direto.**

## Bloqueios

### Bloqueio 1 `tsc` não estava no PATH do Windows

**Contexto:** tentativa de rodar `tsc --noEmit` diretamente no terminal após a migração de tokens.

**O que tentei:**
1. `npx tsc --noEmit` resolveu o pacote `tsc@2.0.4` (errado, não é o TypeScript).
2. `node_modules/.bin/tsc` via Bash caminho inválido no Windows.
3. `.\node_modules\.bin\tsc` via PowerShell não reconhecido.
4. `node .\node_modules\typescript\lib\tsc.js` módulo não encontrado porque devDependencies não estavam instaladas.

**Causa:** a máquina tem `omit=dev` no npm global, então `tsc` (devDependency) não estava em `node_modules`. Resolvido usando `npm run build` que chama o `tsc` interno do script.

### Bloqueio 2 devDependencies não instaladas pelo `npm install` padrão

**Contexto:** após o shadcn CLI instalar os pacotes Radix, as devDependencies (`eslint`, `typescript`, etc.) não estavam em `node_modules`.

**Causa:** configuração global do npm com `omit=dev`. O `npm install` simples instalou apenas dependências de produção (59 pacotes). Resolvido com `npm install --include=dev` explícito.

**Aprendizado para este projeto:** sempre usar `npm install --include=dev` nesta máquina.

### Bloqueio 3 ESLint global v10 interferindo no `npm run lint`

**Contexto:** após o bloqueio 2, `npm run lint` falhou com erro de ESLint v10 não encontrando `eslint.config.js`.

**Causa:** como o ESLint local (v8) não estava instalado, o script do npm encontrou o ESLint global (v10), que exige o novo formato de config. O projeto usa `.eslintrc.cjs` (formato v8). Resolvido após `npm install --include=dev` instalar o ESLint local v8.

### Bloqueio 4 `esbuild.exe` bloqueado ao instalar `lucide-react`

**Contexto:** tentativa de `npm install lucide-react` falhou com `EBUSY: resource busy or locked`.

**Causa:** processo do Vite (dev server) estava rodando e bloqueando o arquivo. Resolvido com retry após aguardar liberação do processo.

### Bloqueio 5 CLI shadcn não instalou `lucide-react` automaticamente

**Contexto:** após adicionar os 12 componentes, o lint apontou `import/no-unresolved` para `lucide-react` em `sheet.tsx`.

**Causa:** o CLI `shadcn add sheet` gera o componente com import de `lucide-react` mas não adiciona a dependência ao `package.json`. Resolvido com `npm install lucide-react` separado.

## Aprendizados para o Projeto

- Esta máquina tem `omit=dev` no npm global. Sempre usar `npm install --include=dev` ao instalar pacotes neste projeto.
- O CLI `npx shadcn@latest add` não instala `lucide-react` mesmo quando o componente gerado o importa. Verificar imports após cada `add`.
- O comando `shadcn add` (sem `init`) modifica `tailwind.config.cjs` mesmo assim adicionando `darkMode` e keyframes necessários. É seguro, mas deve ser verificado após a execução.
- A análise de impacto antes de refatorar tokens é eficaz: mapeamento de frequência por token revelou que a migração completa era trivial (7 find-replace sem ambiguidade), tornando a abordagem de bridge desnecessária mesmo com aparência de risco inicial.
