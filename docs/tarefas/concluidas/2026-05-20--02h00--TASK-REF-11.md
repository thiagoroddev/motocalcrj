## Decisões Tomadas

- **`migrarPerfil()` inline em `criarEstadoInicial`** ao invés de `migrarPerfil.ts` separado: custo/benefício baixo para uma migration única. DT-6 registrada como "endereçada parcialmente". `migrarPerfil.ts` permanece recomendação para TASK-8.x.
- **DT-13 deferido para TASK-REF-12:** a migração de index-based para km-based key requer leitura do preset JSON em runtime durante a migration, adicionando dependência desnecessária antes do override ser sequer lido pelo calculador.
- **INV-MANUT-1 com `return state` silencioso:** consistente com o pattern dos demais guards do reducer. Componentes de UI devem validar antes de despachar.
- **`servicosMaoDeObra` descartado sem tentar preservar valores:** campo nunca foi lido pelo calculador (orphan confirmado). Sem perda funcional para o usuário.

## Aprendizados Para o Projeto

- Campos "orphan" (armazenados mas nunca lidos) acumulam silenciosamente quando não há teste que os exercite. Identificados aqui pela análise pré-ADR-004. Vale considerar testes de integração que verifiquem que campos do perfil são efetivamente consumidos pelo calculador.
- Migration inline em `criarEstadoInicial` é simples e funcional para migrations pontuais. Para múltiplas versões acumuladas, `migrarPerfil.ts` com pipeline de versões é mais seguro.
