## Execução

### 1. `.github/workflows/lancamento.yml` — o veredito de publicar ganha URL

`workflow_dispatch` com input de URL. Etapas: `npm ci` → `build` (o portão precisa de `dist/` para
orçamento de bundle e varredura de segredos) → `npx -y lighthouse` gerando
`relatorios/lighthouse.json` → `npm run gate:lancamento` → **upload de artefato com `if: always()`**.

O `if: always()` é o detalhe que importa: **o artefato de um run REPROVADO é o mais útil de todos** —
é a evidência de por que não se pode publicar. Retenção de 90 dias.

**Gatilho manual, não tag — por correção, não preguiça.** O portão mede a **produção servida**.
Disparar em tag mediria a produção **anterior**, porque a Vercel ainda não terminou o deploy: o run
daria verde sobre o artefato errado, que é pior que não rodar. E o workflow não consegue confirmar
sozinho que a produção já é o commit dele, porque **o hash dos assets difere entre ambientes de
build** — comprovado na `TASK-RNF-9.1` (`D4NilPDQ` local vs `k78uyd8M` na Vercel). Resolver exigiria
token da Vercel: credencial no repositório para economizar um clique.

## Decisões Tomadas

- **Gatilho manual.** Ver acima. Documentado no cabeçalho do workflow com o motivo, para ninguém
  "melhorar" isso depois trocando por `on: push: tags`.
- **O portão passa a reprovar hoje, e isso é o comportamento certo.** Adicionar o item 9 levou o
  veredito de `SIM` para `NÃO`. Não é regressão: é o portão registrando que a configuração de
  segurança da plataforma **não foi confirmada por ninguém**. Publicar não devia estar verde nesse
  estado. Um clique em cada toggle e uma edição de três palavras no registro resolvem.
- **Status `desligado` exige motivo na mesma linha.** Desligar item de segurança é decisão; decisão sem
  motivo registrado é esquecimento.
- **Item 9 valida `ligado`, não só a data.** Poderia ter validado apenas "alguém olhou nos últimos 90
  dias", o que passaria com um registro cheio de `a confirmar`. Exigir `ligado` transforma o registro
  em afirmação de verdade — humano-mantida, e por isso falível, mas afirmação.

## Aprendizados Para o Projeto

- **Gate novo que já nasce vermelho pode estar certo.** O reflexo é ajustar o limiar até ficar verde —
  foi o que a `TASK-CHORE-024` teve que fazer com o LCP, por ruído de medição. Aqui é o oposto: o
  vermelho descreve a realidade (ninguém confirmou os toggles) e ajustar para verde seria mentir.
  A diferença entre os dois casos é se o vermelho é **ruído** ou **fato**.
- **Verificação fraca, declarada como fraca, vale mais que silêncio.** Não dá para checar toggle de
  plataforma sem token. Registrar quem olhou e quando, e dizer explicitamente que é só isso, mantém o
  assunto visível sem inventar garantia.
- **Gatilho de CI tem semântica.** `on: push: tags` parece o lugar óbvio para um portão de lançamento e
  mediria o artefato errado. Quando o gate observa um sistema externo, o gatilho tem que respeitar o
  tempo desse sistema, não o do repositório.
