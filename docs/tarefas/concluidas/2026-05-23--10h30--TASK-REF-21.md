## Análise de Impacto

**Data da análise:** 23/05/26

### Mudança Proposta

ADR-005 §"Reconsiderar booleanos de presença de custo": um custo está presente sse `valor > 0`. O boolean `seguro.tem` duplica essa noção e gera bug B-1 (editar valor em SecaoFinanceiro sem efeito quando `tem===false`). Removido `tem`; presença passa a ser derivada de `valorAnual > 0` em todo o app. Corrige B-1, simplifica modelo, alinha com REF-19 (remoção de campos mortos).

### Decisões IA tomadas (aprovadas pelo humano)

1. **Toggle Sim/Não no Passo7 preservado como UX.** Estado local; quando "Não" → dispatch com `valorAnual: 0`. Onboarding fica intuitivo; presença passa a ser derivada no resto do app.
2. **`calcularCustoSeguroAnual(valorAnual)` defensiva:** `return valorAnual > 0 ? valorAnual : 0`. Alinha com "presente sse > 0"; robusto contra invariante quebrado.
3. **Migração v9→v10 preserva intenção do usuário:** se `tem === false`, força `valorAnual: 0` antes de deletar `tem`. Sem isso, perfis em que o usuário desligou seguro mantendo valor antigo "esquecido" passariam a contar pós-migração.
4. **Excluído `CampoSwitch.tsx`** (código morto criado por REF-14; ADR-005 proíbe switch em Ajustes).

## Decisões Tomadas

- **Toggle Sim/Não no Passo7 mantido como UX:** estado local do componente. Quando o usuário clica "Não", o dispatch envia `valorAnual: 0` e `empresa: null`, removendo a presença do seguro. Quando clica "Sim", input aparece para preencher. Conceitualmente o boolean morre no domínio, mas continua vivo no formulário pela ergonomia.
- **`calcularCustoSeguroAnual` defensivo (`valorAnual > 0 ? valorAnual : 0`):** alinha com a semântica "custo presente sse > 0" da ADR-005. Robusto contra entradas negativas (que não deveriam acontecer, mas evitam bug silencioso). Teste defensivo adicionado.
- **Migração v9→v10 com force-zero quando `tem===false`:** mitigação obrigatória contra o caso "perfil com `tem: false` + `valorAnual: 929.96` antigo esquecido" — pós-migração ingênua, esse perfil passaria a contar seguro. Detectado durante análise; sem a mitigação, REF-21 introduziria regressão silenciosa.
- **`perfilPadrao.seguro.valorAnual: 929.96 → 0`:** coerente com ADR-005 (perfilPadrao não presume custos) e com BG-004 (reset zera). O Passo7 mostra "0" como string inicial — pode ser melhorado para placeholder vazio em task futura se quiser sugestão pré-populada.
- **Bug de ordem na migração detectado e corrigido em 1 minuto:** inseri v9→v10 antes da v8→v9 (linha 688). Como migrações em cascata dependem de `dados.schemaVersion` no momento da entrada em cada `if`, ordem ascendente importa. Reordenado para v8→v9 antes de v9→v10. Lição reforçada do REF-19.
- **Cascata v8→v9→v10 cobre fixture v6 também:** a fixture (schemaVersion 6) ainda exercita v6→v7→v8→v9→v10 no load. Teste explícito `cascata v8 → v10` cobre os dois saltos novos juntos.

## O Que NÃO Foi Feito (e Por Quê)

- **Padronizar todos os outros booleanos de presença de custo:** ADR-005 menciona o tema genericamente, mas `seguro.tem` era o único caso atual. `gastosCustom[].ativo` continua existindo, mas é semanticamente diferente (toggle individual do gasto, não "presença" derivável de valor — o usuário pode querer pausar um gasto sem zerar o valor). Fora de escopo.
- **Melhorar UI do Passo7 quando `valorAnual === 0`:** mostrar placeholder vazio em vez de "0" como string inicial seria UX melhor. Mantido como está — funciona, é minor. Task futura se valer.
- **Pré-popular sugestão de seguro em Passo7 (ex.: 929.96):** o app antigo presumia esse valor no perfilPadrao. Removido por ADR-005. Reintroduzir como sugestão UI (sem ir para o estado) seria outra task.

## Aprendizados Para o Projeto

- **Migração com mitigação > migração ingênua.** A v9→v10 inicial naïve seria só `delete novoSeguro.tem`. Mas isso introduziria regressão silenciosa em perfis com `tem: false + valorAnual: 929.96 esquecido`. A análise de impacto pegou esse caso antes de implementar — mitigação `if (tem === false) valorAnual = 0` é 3 linhas mas vale por todos os perfis em produção.
- **Booleanos "tem X" são red flags pós-ADR-005.** A heurística "se posso derivar de `valor > 0`, não preciso de boolean" pode ser aplicada a futuros campos. `seguro.tem` foi o caso prático; outros similares (se aparecerem) devem ser questionados na revisão.
- **Erro de ordem em migrações é frequente o suficiente para virar checklist.** Tanto REF-19 quanto REF-21 precisaram pensar na ordem (v8→v9 antes de v9→v10). Sugestão: ao adicionar nova migração v(N)→v(N+1), confirmar visualmente que o novo `if (dados.schemaVersion === N)` vem DEPOIS de todos os `if (... === M)` com M < N.
- **Estado local UX ≠ estado de domínio.** O `tem` no Passo7 morre no payload do dispatch mas vive no `useState` do componente. Distinção válida — formulário pode ter estado ergonômico que não vai para o modelo. Quando a UI tem um conceito ("o usuário disse não") que se mapeia para outra coisa no domínio ("valor zero"), separar os dois é OK.
