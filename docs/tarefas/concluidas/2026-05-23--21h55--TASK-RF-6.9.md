- **Valor único acumulado** (não recorrência mensal). Esse passa a ser o padrão geral do app para qualquer valor personalizado futuro, fechando uma lacuna deixada pela remoção dos Registros (ADR-003).

- Presets não podem ser deletados; sem botão de adicionar.

## Decisões Tomadas

- **Valor único acumulado (sem recorrência).** Multa/Sinistros/Outros não são eventos recorrentes mensais - o usuário soma na cabeça o total no ano e edita o campo único; quando vier novo evento, edita somando.
- **Lista fechada (sem cadastro avulso).** "Outros" cobre o coringa para o que não couber em Multa/Sinistros - evita o problema de ter formulário de adição livre que ninguém usa direito.
- **Auto-ativação do toggle ao informar valor > 0.** Conveniência: ao declarar um custo, o usuário implicitamente quer que ele entre. Zerar **não** desativa - mantém controle explícito de quem zerou.
- **Popup só com input + Cancelar/Salvar.** Sem extras. Enter salva.
- **Parser de valor tolerante a vírgula e ponto.** O usuário brasileiro escreve `1.234,56` - o parse limpa pontos de milhar e troca vírgula por ponto antes do `Number()`.
- **Edição visível por ícone de lápis explícito.** Reforça a percepção de que essa é a única categoria editável direto na tela. Texto do rodapé explicita.
- **Migração descarta gastos custom antigos.** App ainda não tem usuários reais; preservá-los como "itens deletáveis" criaria caminho de código de exceção que não pode mais ser criado.

## Aprendizados Para o Projeto

- O padrão "valor único acumulado" (vs recorrência mensal) é o jeito leve de capturar custos pontuais sem reabrir a complexidade dos Registros. Para qualquer custo futuro que não tenha periodicidade natural, esse deve ser o default.
- Quando uma task original prevê um campo novo (ex.: "adicionar categoria") e o alinhamento com o usuário muda a direção (ex.: "fechar a lista de itens em vez de abrir a categoria"), o ganho de simplificação costuma ser maior do que o investimento em flexibilidade. Vale rediscutir o escopo antes de codar.
- Migrações que descartam dados antigos são aceitáveis em fase pré-produção, mas exigem registro explícito (commit + ADR/task) para que se torne rastreável depois.
- Auto-ativar o toggle ao informar valor > 0 (mas **não** desativar ao zerar) é uma assimetria proposital: declarar custo é gesto de inclusão, zerar pode ser limpeza temporária.

## Correção Pós-Conclusão - 23/05/26 22:23

### Bug reportado pelo usuário

Após a conclusão, validação visual mostrou que os 3 presets (Multa = R$ 200, Sinistros = R$ 1.500, Outros = R$ 10) com toggle ativo **não somavam** ao total da seção Imprevistos nem ao total geral. Em "Ano", Imprevistos exibia R$ 182,00 (apenas a retífica de cabeçote sugerida); em "Mês", R$ 15,17 (a amortização da retífica convertida) - sinal de que a soma das retíficas funcionava, mas a dos presets não.

### Diagnóstico

Bug **preexistente**, latente há muito tempo, exposto pelos presets sempre presentes.

`PaginaDetalhamento.tsx:86` e `utils/calculos.ts:426` ambos fazem:

```ts
filtros.gastosCustom ? custos.gastosCustom.total : 0
```

`filtros.gastosCustom` é derivado por [`categoriasParaFiltros`](src/utils/calculos.ts) que tinha:

```ts
gastosCustom: cat.financiamento, // gastosCustom não tem toggle separado
```

- ou seja, copiava o filtro de financiamento. Como `categoriasAtivas.financiamento` vem `false` por padrão no `perfilPadrao` (moto quitada), `filtros.gastosCustom` ficava `false` e o `custos.gastosCustom.total` (soma dos `valorAnual` dos presets ativos) era zerado.

Antes da TASK-RF-6.9, `gastosCustom` só existia quando o usuário cadastrava manualmente (raro) - o bug ficava silencioso. Com os 3 presets sempre presentes, virou imediatamente visível.

A semântica correta é: Imprevistos não tem toggle de **categoria** (apenas toggles individuais por linha - `g.ativo` para presets, `filtros.imprevistosSugeridos[id]` para sugeridos). Logo `filtros.gastosCustom` deveria ser sempre `true`. Os toggles individuais já são respeitados em `calcularCustoGastosCustomAnual` (`gastosCustom.filter((g) => g.ativo)`).

### Correção

- `src/utils/calculos.ts:693`: `gastosCustom: cat.financiamento` → `gastosCustom: true`, com comentário explicando o porquê.
- `src/utils/calculos.test.ts`: novo describe `categoriasParaFiltros` com teste de regressão (`'gastosCustom sempre true'`).

### Testes pós-correção

- `npm run test`: ✅ 111 verdes.
- `npx tsc --noEmit`: limpo.

### Aprendizado adicional

Comentário de código que diz "X não tem toggle separado" e implementa "X copia o toggle de Y" é incoerente - copiar de outro toggle É ter um toggle, só que invisível. Quando uma decisão de UI exige que algo não seja controlado, o filtro correspondente deve ser **constante**, não **derivado de outra coisa**. Esse padrão de "derivar de qualquer fonte por inércia" é o tipo de bug que fica latente até alguém mexer no caminho - como aconteceu aqui.
