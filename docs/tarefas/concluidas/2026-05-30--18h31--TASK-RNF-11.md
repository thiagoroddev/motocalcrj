## Decisões Tomadas

- **Boundary na raiz, fora dos providers (`main.tsx`, não dentro do `App`):** assim captura erro vindo do `ThemeProvider`/`PerfilProvider` também, não só das telas.
- **Reset extraído em função pura `resetarPerfilStorage(storage)`:** o `window.location.reload()` não existe em ambiente node; separar o `storage.limpar()` (testável) do reload (handler) permite unit test sem DOM.
- **Sem renderização nos testes:** vitest roda em `environment: 'node'`, sem DOM nem `@testing-library`. Render-test exigiria adicionar `jsdom` + lib - expansão de escopo deixada como possível CHORE. Cobertura por método estático + reset, coerente com o projeto (zero testes de render hoje).
- **Dois botões (Recarregar + Resetar):** recarregar é a tentativa não-destrutiva primeiro; resetar é o último recurso (destrutivo, estilo `destructive`).

## O Que NÃO Foi Feito (e Por Quê)

- **Botão "Exportar dados" no fallback:** depende da TASK-RF-7.1 (Export/Import), inexistente. Deixado um comentário marcando o ponto de extensão em `aoResetar`.
- **Teste de renderização do fallback:** sem DOM no vitest; não vale adicionar jsdom/testing-library só para isto nesta tarefa (vira decisão/CHORE separada).
- **Captura de erros assíncronos / event handlers:** fora do alcance de ErrorBoundary por design do React - comportamento esperado, não é lacuna.

## Aprendizados Para o Projeto

- **Todo app com persistência local deveria nascer com ErrorBoundary + escape hatch.** Junto com a RNF-10, fecha o ciclo de robustez: dados ruins não brickam (RNF-10) e erro de render não prende o usuário (RNF-11).
- **Posição do boundary importa:** fora dos providers pega mais erros. Boundary dentro do `App` deixaria erro de provider escapar.
- **Ambiente de teste molda o design:** sem DOM, extrair lógica pura (método estático, helper de reset) é o caminho para cobertura - em vez de forçar a infra de render só para um componente.
