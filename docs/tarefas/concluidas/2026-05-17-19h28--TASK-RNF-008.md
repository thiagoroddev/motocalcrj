## Objetivo

Avaliar e executar a migração para React 19 e React Router v7, conforme ordem definida na ADR-001, após estabilização da stack base (Vite 6, TS 5.8, Tailwind v4, ESLint v9).

## Planejamento Aprovado

**Bump de versões:**
- `react` / `react-dom`: 18.3.1 → ^19.0.0
- `@types/react` / `@types/react-dom`: 18.x → ^19.0.0
- `react-router-dom`: 6.27.0 → ^7.0.0

**Estratégia React Router v7:** modo biblioteca (sem migração para framework mode). API v6 preservada integralmente.

**Estratégia React 19:** atualizar tipos + verificar componentes shadcn. Regenerar apenas se gerar erros de compilação.

## Execução

- `npm install` concluído — warnings de peer deps esperados do Radix UI (override automático pelo npm).
- Versões instaladas: react@19.2.6, react-dom@19.2.6, react-router-dom@7.15.1, @types/react@19.2.14, @types/react-dom@19.2.3.
- Radix UI deduplicado corretamente em React 19 — todos os pacotes `@radix-ui/*` usando `react@19.2.6 deduped`.
- Shadcn components: nenhum erro de compilação com `forwardRef` + React 19 — sem necessidade de regenerar.

## Decisões Tomadas

- Usar modo biblioteca do React Router v7, não framework mode: projeto é SPA/PWA puro sem loaders/actions Remix. Mudança seria arquitetural sem ganho prático agora.
- Não regenerar componentes shadcn: `forwardRef` em React 19 gera apenas deprecated warnings em runtime, não erros de compilação. O risco de regressão visual na regeneração supera o ganho de remover warnings.
- Não adicionar future flags do RR v7 no `<BrowserRouter>`: opcional e sem impacto funcional imediato.

## O que NÃO foi feito e por quê

- Migrar para framework mode do React Router v7: mudaria arquitetura inteira; sem benefício para SPA/PWA.
- Adotar Server Components / Server Actions: app é CSR/PWA.
- Regenerar componentes shadcn para remover `forwardRef`: warnings em runtime, não erros; risco de regressão visual supera benefício.
- Adicionar future flags do RR v7: opcional; propor como TASK-CHORE se necessário no futuro.
