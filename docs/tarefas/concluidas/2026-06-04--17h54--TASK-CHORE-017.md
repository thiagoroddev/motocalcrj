## Decisões Tomadas

- **Usar REST da Parallelum, não SDK Go:** o repositório `parallelum/fipe-go` é SDK gerado para a API REST; no projeto TS/Vite, chamar a REST direto evita introduzir Go no toolchain.
- **Runtime continua sem depender da nova API:** a atualização mensal grava `tabelaFipe` nos presets. O app segue consumindo valores hardcoded/fallback.
- **Dry-run como rotina segura:** `npm run fipe:check` permite verificar mês, modelo e anos antes de escrever nos JSONs.

## O Que NÃO Foi Feito (e Por Quê)

- **Não trocar `src/services/fipeService.ts`:** fora do escopo. A necessidade imediata é atualizar os valores hardcoded sem consulta manual.
- **Não automatizar agenda mensal no CI:** o comando existe; agendamento pode virar workflow separado se desejado.
- **Não adicionar dependências:** Node 18+ já fornece `fetch`.

## Revisão (Segunda passada — revisor independente, 04/06/26)

### Modo
Revisão IA independente (módulo 21), contra o código. **Verificações:** `node --check` no script → sintaxe OK; presets conferidos (Pop `codigoFipe: "811132-4"`, 2016–2024; Factor `codigoFipe: "827104-6"`, 2017–2025 — ambos numéricos e schema-válidos, 294 testes verdes incluindo o contrato `tabelaFipe: Record<string, number>`); `package.json` com `fipe:check`/`fipe:update`.

### ✅ Bom
- **Estratégia text-based (regex) preserva os `_fonte`/formatação** dos presets — `JSON.parse` + `stringify` perderia a documentação rica embutida. Decisão acertada.
- `substituirObrigatorio` **falha alto** se algum campo não casar — não há update parcial silencioso.
- **Idempotente** (guard `novoTexto !== texto` + dry-run pós-update "sem mudanças").
- `parseValorBRL` robusto (R$/milhar/vírgula, rejeita não-finito/≤0); `fetch` com `AbortController` + timeout 15s.
- Descoberta automática de `codigoFipe` (bootstrap por marca+nomeFipe); como ambos os presets já têm `codigoFipe`, o caminho frágil de fuzzy-match fica fora do uso recorrente — bom (a `nomeFipe` da Factor, "YBR 125i FACTOR ED/FLEX", seria difícil de casar por normalização).
- Runtime do app intacto (segue hardcoded); zero nova dependência (Node `fetch`).

### 🔴 Bloqueante
Nenhum.

### 🟡 Importante
**A direção "BrasilAPI não será mais usada" não está registrada nem implementada — fica um mecanismo paralelo órfão.**
- `src/services/fipeService.ts` + onboarding **Passo 3 ainda chamam a BrasilAPI em runtime** (a task explicitamente não tocou). Hoje coexistem dois mecanismos de FIPE.
- **TASK-RNF-014** (pendentes: "Validar resposta da FIPE/BrasilAPI com Zod") fica **provavelmente obsoleta** — não faz sentido endurecer uma API que será removida.
- A mudança de **como o FIPE funciona** (lookup runtime → hardcoded atualizado por script mensal) é arquitetural e muda a UX do Passo 3 (valor ao vivo → valor da `tabelaFipe`); sem registro, outra IA reintroduz a BrasilAPI.
- Docs (`_glossario.md` "BrasilAPI / FIPE" e "FIPE Cache", `requisitos`) descrevem o fluxo runtime atual e ficarão stale quando o `fipeService` sair.

→ **Gerada TASK-REF-36** (aposentar BrasilAPI: Passo 3 usa `tabelaFipe` hardcoded + remover/retirar `fipeService` + atualizar docs) e **anotada a TASK-RNF-014** para re-avaliação. Recomendado um **ADR** registrando a decisão "FIPE hardcoded + script mensal" antes de executar a REF-36 (decisão de produto/arquitetura — fica com o humano).

### 🟢 Sugestão
- **Contrato `_fonte` implícito:** o script exige `_fonte.dataColeta`, `_fonte.codigoFipeNota` e `_fonte.anoModelo` em **todo** preset (`substituirObrigatorio` lança se faltar). Aceitável para 2 presets; ao adicionar modelos, ou documentar esse "contrato de `_fonte`" ou tornar esses 3 replaces opcionais.
- **Sem isolamento por preset:** um erro de rede aborta o batch (escrita é por-preset, então há progresso parcial; idempotente no re-run). Um `try/catch` por preset com resumo no fim seria mais amigável.
- `writeFile` direto (sem temp+rename): crash no meio da escrita pode corromper o JSON (baixo risco em script manual; o schema pega no próximo teste).
- A sugestão do autor (GitHub Action manual/scheduled abrindo PR com o diff) é boa e fecha o loop mensal.

A ressalva é a 🟡: a direção de aposentar a BrasilAPI precisa de tarefa de follow-up (TASK-REF-36), re-avaliação da RNF-014 e, idealmente, um ADR — senão fica um mecanismo paralelo com docs divergentes.
