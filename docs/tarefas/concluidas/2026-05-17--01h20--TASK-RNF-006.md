## Decisões Tomadas

- **Não regenerar os 12 componentes shadcn:** build e lint passaram sem alteração dos componentes. Os class names são idênticos entre v3 e v4. Regenerar via `npx shadcn@latest add --overwrite` injetaria CSS variables em `index.css`, conflitando com o tema já configurado. Risco sem benefício componentes mantidos.
- **`accent` / `accent-foreground` adicionados ao tema:** `button.tsx` (gerado pelo shadcn) usava `hover:bg-accent` sem este token no tema anterior. Adicionado mapeamento em `@theme inline` e valores em `:root` e `.light`. Isso corrige um bug pré-existente, não introduz comportamento novo.
- **Formato `rgb()` em `:root`:** variáveis migradas de valor bare `13 19 33` para `rgb(13 19 33)`, necessário para que `color-mix()` do v4 processe opacidade arbitrária (`bg-primary/20` etc.) corretamente.
- **`@theme inline` em vez de `@theme`:** escolhido para que tokens de cor referenciem variáveis CSS em runtime, habilitando troca de tema light/dark via classe `.light` sem recompilar.

## Aprendizados para o Projeto

- Em Tailwind v4, `@theme inline { --color-*: var(--*) }` com `:root { --*: rgb(...) }` é o padrão correto para temas dinâmicos (light/dark via classe) não usar `@theme {}` direto para cores que mudam.
- Componentes shadcn gerados para v3 funcionam em v4 sem regeneração desde que os tokens de cor estejam mapeados em `@theme inline`.
- Classes de opacidade arbitrária (`bg-primary/20`) funcionam em v4 via `color-mix(in oklab, ...)` automaticamente, desde que os valores em `:root` sejam cores válidas em CSS (ex: `rgb(0 120 255)`, não `0 120 255`).
- `postcss` e `autoprefixer` não são necessários em Tailwind v4 com `@tailwindcss/vite`.
