## Bug

`perfil.financeiro.responsabilidadeAluguel` (3 campos `documentos`/`manutencao`/`seguro` × `eu`/`locador`/`dividido`) era definido no onboarding (Passo6Responsabilidade - "Passo 8 de 9: Quem paga o quê?") mas não tinha tela de edição em Ajustes. Usuário de moto alugada ficava preso na escolha inicial - só conseguia mudar zerando o perfil e refazendo o onboarding. Bug funcional silencioso: o cálculo já consumia o valor (`fatorResponsabilidade` em `calculos.ts:501-509`), o usuário só não tinha como reconfigurar.

## Decisões tomadas

- **Action dedicada `SET_RESPONSABILIDADE_ALUGUEL { config: Partial<ResponsabilidadeAluguel> }`.** Padrão de `SET_SEGURO`: aceita config parcial e faz spread. Permite editar 1 campo atomicamente sem precisar reler `responsabilidadeAluguel` inteiro. Onboarding tinha `useState({...})` local + `SET_ONBOARDING_CAMPO` no avançar - substituído por dispatch direto da action nova no clique.
- **Widget `Segmentado` em Ajustes**, mantendo padrão dos outros cards da tela (`SecaoUsoDiario`, `SecaoSituacaoLegal`). No onboarding mantive os botões custom existentes (visual mais expansivo, padrão dos Passos) - os dois layouts coexistem porque vivem em contextos visuais diferentes.
- **`BotaoReset` no card** zerando os 3 a `'eu'` (default do `perfilPadrao`). Consistente com `SecaoUsoDiario`/`SecaoSituacaoLegal`/`SecaoUltimasManutencoes`.
- **Card só renderiza quando `situacaoMoto === 'alugada'`** (retorna `null` caso contrário). Paralelo a `CampoFinanciamento`, que só renderiza para financiada ou alugada. Mudança de `situacaoMoto` em `SecaoSituacaoLegal` faz o card sumir/aparecer na mesma frame (reativo via `usePerfil`).
- **Componente separado, não dentro de `SecaoSituacaoLegal`.** Foi pedido explícito do usuário ("abaixo do card 'Situação Legal'"). Renderizado no `PaginaAjustes.tsx` logo depois do `<SecaoSituacaoLegal>`.
- **Label "Responsabilidade do aluguel".** Mais descritivo no contexto de Ajustes do que o "Quem paga o quê?" do onboarding (que é mais cativante mas pressupõe que o usuário acabou de ler a explicação).
- **`RESETAR_AJUSTES_PADRAO` NÃO toca `responsabilidadeAluguel`.** Reset zera custos (alimentação, internet, seguro, financiamento, imprevistos) per ADR-005 - responsabilidade do aluguel é configuração estrutural, no mesmo nível que `situacaoMoto`/`parcelaMensal`/`aluguelMensal` que também não são tocados pelo reset.
- **Refator do Passo6Responsabilidade.** Substituí `useState({...perfil.financeiro.responsabilidadeAluguel})` + `SET_ONBOARDING_CAMPO` no `salvarEAvancar` por dispatch direto de `SET_RESPONSABILIDADE_ALUGUEL` no clique de cada opção. Vantagens: (a) elimina estado intermediário; (b) padroniza onde os dois pontos de edição usam a mesma action; (c) leitura direta do `perfil.financeiro.responsabilidadeAluguel` (não precisa mais sincronizar em `useState`).
- **a11y dos rótulos das 3 linhas do card:** mantive `<p className="text-xs text-muted-foreground">` (sem `<Label htmlFor>`) - `Segmentado` é um grupo de botões, não `<Input>`, então a rule de TASK-RNF-10 não se aplica.

## Aprendizados Para o Projeto

- Quando o onboarding define um campo via `SET_ONBOARDING_CAMPO` (assinatura genérica que escreve `perfil[campo] = valor`), **toda edição posterior daquele campo precisa de uma action dedicada** - senão fica sem caminho de escrita atômico fora do onboarding. Padrão geral: action tipada por campo, mesmo que o onboarding também grave por ela.
- Manter `useState({...perfil.X})` em uma página de onboarding só faz sentido se houver um botão "Cancelar" - sem ele, a cópia local é overhead. Leitura direta + dispatch no clique é o caminho coerente.
- "Card só aparece quando estado X" é um padrão recorrente no projeto (`CampoFinanciamento` por `situacaoMoto`, agora `CampoResponsabilidadeAluguel`). Vale aplicar consistentemente: o componente devolve `null` quando a condição falha, e quem renderiza não precisa saber da condição.
- Bugs "silenciosos por falta de caminho de escrita" são particularmente nocivos: o cálculo consumia o campo, mas o usuário só conseguia editá-lo zerando tudo. Vale uma auditoria genérica de quais campos do perfil só são escritos pelo onboarding - se algum afeta cálculo, precisa de tela de edição em Ajustes.
