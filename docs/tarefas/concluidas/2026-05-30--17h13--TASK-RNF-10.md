## Decisões Tomadas

- **Validar com `presetEntrySchema` (envelope + perfil juntos), não só `perfilSchema`:** uma passada valida `presetId/nome/datas` e o `perfil` migrado de uma vez.
- **`preservarCorrompido()` é best-effort com try/catch interno:** se o próprio `localStorage` falhar (quota, modo privado), preservar não pode lançar e re-brickar a inicialização - o objetivo é justamente nunca travar.
- **Exportar `criarEstadoInicial`:** necessário para testar o fallback com storage injetado, mantendo o padrão de injeção de dependência já usado no Provider.
- **zod (default) descarta chaves desconhecidas:** um perfil de "versão futura" com campo extra passa na validação (campo extra removido). Comportamento tolerante e desejável - não brickar por causa de um campo que o app atual não conhece.

## O Que NÃO Foi Feito (e Por Quê)

- **Reparo de perfil inválido (alternativa B da ADR-010):** descartado por decisão - preferimos falha visível e recuperável a mascarar bug de migração com dado "meio certo".
- **UI para exportar/recuperar o blob `.corrupted`:** fora do escopo. É gancho natural para a TASK-RNF-11 (ErrorBoundary com escape hatch) e a TASK-RF-7.1 (Export/Import). O blob fica preservado aguardando essas features.
- **Validação no fluxo `IMPORTAR_PERFIL`:** o validador (`perfilSchema`/`presetEntrySchema`) já está disponível, mas a action `IMPORTAR_PERFIL` ainda não tem chamador de UI (RF-7.1 não construída). A validação será plugada quando a RF-7.1 montar a tela de import - registrado para não esquecer.

## Aprendizados Para o Projeto

- **Migração `as any` + zero validação = bomba-relógio em app localStorage-only.** Validar a *saída* da migração (não a entrada) é o ponto certo: a migração normaliza versões antigas, o schema confere o resultado. Padrão reutilizável para qualquer dado que entra de fora (import RF-7.1, FIPE cache).
- **`expectTypeOf` no tsc é a cola que mantém schema e tipo honestos** sem custo de runtime. Sempre que houver um schema espelhando um tipo, vale o teste de compatibilidade.
- **Código de recuperação não pode ter o mesmo modo de falha que tenta evitar:** `preservarCorrompido` é best-effort justamente porque rodar no caminho de erro - se lançasse, re-brickaria.
