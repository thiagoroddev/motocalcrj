## Decisões Tomadas

- **Imprevistos sugeridos usam semântica opt-in:** `undefined` não ativa custo. Só `true` explícito soma no total.
- **Retíficas aparecem sempre em Imprevistos:** isso mantém o lembrete visível sem inflar a estimativa. A decisão do usuário sobre ativar/desativar fica no Detalhamento.
- **Mão de Obra Excepcional segue como fonte canônica:** preço e intervalo continuam editáveis lá; Imprevistos só consome os valores.
- **Campo `precoMaoDeObra` não foi renomeado:** para evitar migração maior. A UI e docs agora explicitam que, em excepcionais, o valor representa peças + mão de obra.

## Aprendizados Para o Projeto

- Itens corretivos de alto custo precisam ser opt-in no Detalhamento, mesmo quando têm valor anual estimável.
- Para filtros de sugestão, `undefined` deve significar desligado; reaproveitar a semântica tristate de Manutenção liga custo por acidente.
- Quando dois lugares mostram a mesma entidade com semânticas diferentes (preço cheio × custo amortizado), a UX precisa explicitar a diferença na própria linha + tooltip/popup, senão o usuário entende como bug de cálculo.
- Cuidado ao passar `className="max-w-*"` em `DialogContent`: `tailwind-merge` pode consolidar a classe passada com a base de forma que `w-full` perde efeito e o container colapsa para `min-content`. Prefira não sobrescrever max-w no DialogContent — use o default responsivo da base (`max-w-[calc(100%-2rem)] sm:max-w-lg`).

## Correção Pós-Conclusão — 23/05/26 14:50

### Bug reportado pelo usuário

Após a conclusão da BG-005, o usuário relatou que o valor exibido em `Detalhamento > Imprevistos` para as retíficas era diferente do valor configurado em `Mão de Obra > Excepcional`. Exemplo: retífica de cabeçote configurada em R$ 800 aparecia como R$ 182,00 em Imprevistos (perfil padrão: 18.200 km/ano).

### Diagnóstico

Não era bug de cálculo — eram dois números semanticamente diferentes mostrados sem distinção:

- `Mão de Obra Excepcional` exibe `precoMaoDeObra` (preço cheio do serviço, fonte canônica).
- `SecaoImprevistos` exibia `pp(custoAnual)`, onde `custoAnual = (preco / intervalKm) × kmAnual` (custo anual amortizado, o que entra no total).

A divergência confundia o entregador porque não havia explicação visível do que significava "amortizar".

### Plano aprovado

- Em cada linha de imprevisto sugerido: destaque com o preço cheio (`moeda(precoServico)`) + caption pequena com o impacto anual amortizado (`pp(custoAnual)`).
- Ícone `?` no cabeçalho de Imprevistos + link "entenda" na nota de rodapé. Ambos abrem `Dialog` com explicação textual da amortização, fórmula e exemplo numérico.
- Sem mudar tipos, cálculos ou semântica de toggle. Toggle continua somando `custoAnual` ao total.

### Bug secundário: Dialog renderizando estreito e sem overlay

Após habilitar o popup, o usuário identificou que o Dialog renderizava em uma coluna vertical estreita, com texto quebrando palavra-por-palavra e overlay incompleto. O problema afetava `DialogConfirmacao` e o novo popup de Imprevistos — todos os popups do app.

**Diagnóstico:** `tailwindcss-animate` não está em `package.json`, mas `src/components/ui/dialog.tsx`, `sheet.tsx` e `select.tsx` referenciam classes desse plugin (`animate-in`, `slide-in-from-left-1/2`, `zoom-in-95`, `fade-in-0`, etc.). Tailwind v4 ignora silenciosamente as classes desconhecidas, então o dialog ficava sem animação de entrada e — combinado com `left-[50%] translate-x-[-50%]` em viewport mobile estreito — sem o posicionamento esperado.

**Correção em `src/components/ui/dialog.tsx` (final, após 2 iterações):**
- Removidas todas as classes do `tailwindcss-animate` que não geravam CSS (`data-[state=open]:animate-in`, `slide-*`, `zoom-*`, `fade-*`, `duration-200`).
- Posicionamento final: `fixed left-1/2 top-1/2 -translate-x-1/2 -translate-y-1/2` (centralização via transform — padrão shadcn/ui moderno).
- Largura: `w-full max-w-[calc(100%-2rem)] sm:max-w-lg` — full-width com 16px de margem lateral em mobile; cap de 32rem em telas ≥ 640px.
- Padding responsivo: `p-4 sm:p-6`.
- `max-h-[calc(100vh-2rem)] overflow-y-auto` para conteúdos longos rolarem sem cortar.
- `rounded-lg` aplicado direto (era `sm:rounded-lg`).

**Tentativa 1 (falhou):** usei `inset-x-4 w-auto mx-auto` por inspiração em padrões antigos, mas a combinação resultou em `width: 0` no conteúdo (browser priorizou `w-auto` sobre a constraint do inset). Aparecia só uma faixa vertical com X e scrollbar — sem conteúdo visível.

**Tentativa 2 (não resolveu):** apliquei `w-full max-w-[calc(100%-2rem)] sm:max-w-lg`. Build verde, mas o usuário relatou que o popup continuava renderizando como faixa vertical estreita sem conteúdo. Diagnóstico mais profundo: as classes do `tailwindcss-animate` (`animate-in`, `fade-in-0`, etc.) que eu havia removido eram necessárias não só para animação, mas também para o estado visual final do Radix Dialog em Tailwind v4 (sem `fade-in-0`, o conteúdo pode herdar opacity inicial errada).

**Tentativa 3 (não resolveu o popup novo):** com autorização do usuário para instalar dep nova:
- `npm install tw-animate-css` (versão Tailwind v4 do `tailwindcss-animate`, plugin shadcn/ui).
- `@import "tw-animate-css";` no topo de `src/index.css`.
- `dialog.tsx` restaurado com classes de animação do padrão atual do shadcn/ui (`data-[state=open]:animate-in data-[state=closed]:animate-out fade-in-0 fade-out-0 zoom-in-95 zoom-out-95`).
- Mantida largura responsiva `w-full max-w-[calc(100%-2rem)] sm:max-w-lg`, padding `p-4 sm:p-6`, scroll interno `max-h-[calc(100dvh-2rem)] overflow-y-auto`.

Após essa correção, `DialogConfirmacao` (usado em outras telas) voltou a funcionar perfeitamente. Mas o popup novo da SecaoImprevistos continuava renderizando como faixa vertical sem conteúdo.

**Tentativa 4 (resolveu de vez):** com `DialogConfirmacao` funcionando e o novo popup não, foquei na diferença estrutural:
- O popup novo passava `<DialogContent className="max-w-md">`. O `tailwind-merge` consolidava `max-w-md` (passado) com `max-w-[calc(100%-2rem)] sm:max-w-lg` (base) de forma que **a largura efetiva colapsava para `min-content`** — cada palavra do conteúdo virava uma linha, o popup ficava altíssimo e estreito (1 palavra de largura).
- Além disso, o popup estava dentro de `<Card overflow-hidden>`. Apesar do Portal renderizar fora dessa árvore, removi para reduzir variáveis.
- Mudanças: removido `className="max-w-md"` do DialogContent; popup movido para fora do `<Card>` via Fragment `<>...</>`.

CSS bundle final: 51,73 kB (+5,3 kB vs antes do plugin) — esperado, são as classes utilitárias de animação sendo geradas.

**Nota operacional:** durante a tentativa 3, o `npm install tw-animate-css` inicial removeu node_modules acidentalmente. Recuperado com `npm install --include=dev`. Build voltou a passar; sem perda de código ou config.
