## Planejamento Aprovado

Criar `.github/dependabot.yml` com os ecossistemas `npm` e `github-actions`, frequência semanal e PRs
agrupados para não virar ruído.

**Motivo:** a `TASK-CHORE-020` nasceu porque ninguém olhou para as dependências durante 197 tarefas.
A `TASK-CHORE-024` fez o CI **bloquear** nesse caso, mas bloquear é reativo — só dispara quando alguém
faz push. Repositório parado um mês não revela nada. **O CI é a tranca; o Dependabot é o alarme.**

**Agrupamento decidido pelo humano:** produção e dev separados.

## Execução

### O escopo escrito não cobria a motivação da tarefa

A tarefa dizia "hoje nada avisa quando sai CVE nova → criar `.github/dependabot.yml`". Levantando,
são **três mecanismos distintos**, e o arquivo cobre só um:

| Mecanismo | O que faz | Onde se configura |
|---|---|---|
| Version updates | "saiu versão nova" — PRs agendados | `.github/dependabot.yml` ✅ |
| **Alerts** | **"saiu CVE que te afeta"** | Settings → Code security |
| **Security updates** | PR automático corrigindo a CVE | Settings → Code security |

Ou seja: a parte de CVE — a motivação real — é **toggle na web**, não código. Mesma natureza do branch
protection da `TASK-CHORE-027`. Não é verificável nem acionável por aqui: a API do GitHub responde
`401` sem autenticação nos endpoints `vulnerability-alerts` e `automated-security-fixes`.

### Configuração aplicada

- **Dois ecossistemas:** `npm` e `github-actions`, ambos semanais na segunda às 06:00
  (`America/Sao_Paulo`) — PR no começo da semana, não na sexta à noite.
- **Grupos npm por tipo de dependência** (`producao` e `desenvolvimento`, cada um com `patch` +
  `minor`), espelhando a distinção que o `scripts/audit-prod.mjs` já faz: bump que entra no bundle do
  usuário merece revisão diferente de bump de ferramenta.
- **Majors ficam fora dos grupos** → PR individual. Deliberado: major exige ler changelog, e é
  exatamente o material que a `TASK-CHORE-025` precisa (react-router 8, eslint 10).
- **`github-actions` num grupo só:** 2 usos hoje (`actions/checkout@v4`, `actions/setup-node@v4`),
  risco baixo — segmentar seria cerimônia sem ganho.
- **`open-pull-requests-limit: 5`** e `commit-message.prefix: deps`.

Volume esperado: **0 a 2 PRs por semana**, mais os majors quando aparecerem.

## Decisões Tomadas

- **`prefix: deps` em vez de `chore(deps)`.** O projeto não usa conventional commits — as mensagens
  são frases em português com ID de tarefa. `deps` é curto, sinaliza commit de máquina e não finge um
  padrão que o repositório não segue.
- **Agrupar por `dependency-type`, não num grupo único.** Um PR só teria menos ruído (0-1 por semana),
  mas colocaria bump de `react` no mesmo diff que bump de `prettier`. A distinção prod/dev é a mesma
  que o projeto já usa no gate de auditoria; manter coerência importa mais que economizar um PR.
- **Majors permitidos.** Poderiam ser ignorados para reduzir ruído, mas aí a `TASK-CHORE-025` perderia
  a ajuda: são justamente os PRs que trazem changelog e sinal de compatibilidade para avaliar a
  migração. E o PR de `react-router` 8.x é a **saída do RA-001**, que vence em 27/10/2026.
- **O arquivo documenta o que ele NÃO faz.** O cabeçalho avisa que alerts e security updates são
  configuração na web. Sem isso, quem ler o arquivo em seis meses assume que o alarme de CVE está
  coberto — e não está.

## O Que NÃO Foi Feito (e Por Quê)

- **Ligar os toggles de Dependabot alerts e security updates:** exige acesso autenticado ao painel do
  repositório. Passos para o humano na seção Testes.
- **Renovate** (alternativa mais configurável): o Dependabot é nativo, não exige app de terceiro e
  resolve o caso. Trocar seria decisão arquitetural sem problema medido.
- **`ignore` de dependências:** nenhuma justifica hoje; os majors que vão aparecer são desejados.
- **Auto-merge de PR do Dependabot:** exigiria confiar na suíte para mergear sem olhar. Com 38 bugs no
  histórico descobertos em uso real, não é hora.

## Revisão

Modo Light — arquivo de configuração isolado, sem impacto em código de produção. Três pontos merecem
registro:

- **✅ Bom:** o levantamento evitou entregar a tarefa pela metade acreditando tê-la fechado. "Criar o
  YAML" cumpriria o texto da tarefa e deixaria o problema real (aviso de CVE) sem solução.
- **✅ Bom:** o arquivo documenta a própria limitação. É o oposto do que a análise critica — doc que
  afirma cobertura que não tem.
- **🟡 Importante:** metade desta tarefa é toggle na web e ficou como `NÃO EXECUTADO`. Junto com o
  branch protection da `TASK-CHORE-027`, já são **duas** tarefas cuja conclusão depende de
  configuração fora do repositório. Vale um registro único de "configurações de plataforma" no
  `contexto-projeto-ai.md`, para que ninguém precise redescobrir o que está ligado onde.

**Veredito:** APROVADO COM RESSALVAS — o que é código está verificado; o que é plataforma depende de
confirmação do humano e está rotulado como não executado, não como aprovado.

## Aprendizados Para o Projeto

- **Enunciado de tarefa pode não cobrir a própria motivação.** Esta pedia um arquivo YAML para
  resolver "nada avisa quando sai CVE" — e o arquivo não faz isso. Ler o enunciado como especificação
  fechada entregaria a tarefa com o problema intacto.
- **Parte do "pode ir a público" mora fora do repositório.** Dependabot alerts, security updates e
  branch protection são toggles de plataforma. Nenhum script do projeto consegue verificá-los sem
  token, então eles precisam de registro explícito — senão viram conhecimento que existe só na cabeça
  de quem clicou.
