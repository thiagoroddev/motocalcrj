## Decisões Tomadas

- **Deletar arquivos vermelhos em vez de marcar como obsoletos para sempre:** os banners ⚠️ DESATUALIZADO criados na revisão eram temporários. Conceitos mortos não merecem documentação preservada — quem precisar de fidelidade histórica olha o git log ou a TASK-REF-19.
- **Criar `calculos-visao.md` em vez de reescrever `calculos-api.md`:** o arquivo original tinha 1200+ linhas tentando ser referência detalhada. Manter esse estilo geraria divergência rápida de novo. O novo arquivo é enxuto, aponta para o código como verdade primária, e cobre só o que docs realmente agregam (pipeline, mapa função→tela, riscos arquiteturais).
- **Manter namespace `motocalc:v5:` no localStorage:** descoberto durante a Onda 3 que as chaves estão congeladas em `:v5:` por razão histórica — mudar o namespace exigiria migrar storage de todos os usuários sem benefício real. Documentado com nota explicativa em `aggregate-preset.md` e `estado_inicial.md`.
- **Adiar docs/requisitos para TASK-DOC-010:** requisitos são decisão de produto, não engenharia reversa. Reescrita não cabe na mesma cerimônia. Criada task separada (Strict, Importante, Normal) que pode ser puxada quando fizer sentido.
- **DT-14 considerada endereçada na prática:** quase todas as actions específicas listadas como pendentes (SET_MODO_REVISAO, SET_SITUACAO_MOTO, SET_RESPONSABILIDADE_ALUGUEL etc.) já foram criadas pelas REFs e BG-006 recentes. O `SET_ONBOARDING_CAMPO` continua existindo mas agora só é usado intra-onboarding (uso legítimo).
- **Erro de namespace pego e corrigido em 1 minuto:** assumi premature que `motocalc:` sem versão era o atual. Verificar `perfilStorage.ts` antes de afirmar é lição válida — citação de chave de storage é tipo de detalhe que precisa de confirmação direta.

## Aprendizados Para o Projeto

- **Docs de engenharia reversa decaem mais rápido que docs conceituais.** Os arquivos que sofreram mais foram os que tentavam replicar o código (`calculos-api.md`, `historico-manutencao.md` com TypeScript completo). Os que sobreviveram bem foram os que descreviam **conceitos do mundo real** (aggregate-perfil, entidade-moto). Lição: docs de engenharia reversa devem ser enxutas e apontar para o código.
- **Cerimônia em ondas funciona para refatorações documentais grandes.** Commit por onda preserva pontos de retorno e impede sessão única gigante que pode falhar. Cada onda terminada com verificação (grep, test, lint) deu segurança para a próxima.
- **Banner ⚠️ DESATUALIZADO temporário é melhor que reescrita prematura.** A triagem do dia anterior (TASK criada na revisão) deu visibilidade ao problema sem trabalho prematuro. Quando a reescrita rolou, ela rolou com plano completo.
- **Decisões arquiteturais grandes (como ADR-003) exigem tarefa dedicada de sincronização de docs.** Não basta atualizar pontualmente conforme cada feature toca um arquivo — sobra dívida invisível. Lição para futuras ADRs: incluir item explícito de "varredura de docs" no escopo da própria ADR ou criar TASK-DOC junto.
- **Verificar antes de afirmar.** Erro do namespace `motocalc:` foi pego em 1 minuto, mas ilustra: citar caminho de arquivo, nome de função ou chave de storage = abrir o código antes.
