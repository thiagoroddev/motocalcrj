## Conclusão

- **Estimativa por-item** (`estimativaMaoDeObraPorServico`), efetivo = global OU por-serviço; UI no `CardServico` sincronizada entre o popup do Detalhamento e a aba Mão de Obra (helper único `montarEstimativaMaoDeObra`).
- **Popover dinâmico**: tabela "Composição por troca" (peça + M.O. + total) + amortização, sempre batendo com a linha.
- **Controle global acessível** pelo chip do card de total.
- Correções: skip da peça só no `informado` oficial (editado mantém e soma), popup lendo o serviço efetivo, nome do componente em itens só-serviço.

### ✅ Bom
- **Separação de responsabilidades certa:** o cálculo mantém peça (`manutencao`) e M.O. (`revisao.servicos`) em mapas separados (verdade dos totais) e a fusão é só **visão** (`utils/itensManutencao.ts`). Minimiza o toque no `calculos.ts` (gated) e preserva toda a suíte de totais.
- **Fix de correção real, testado:** o CPK pula a peça só no `informado` oficial; `informado_usuario` (edição) mantém e soma — coberto por teste dedicado, sem quebrar os testes de skip existentes (que usam `informado`).
- **DRY efetivo:** helper único `montarEstimativaMaoDeObra` é a fonte do bundle para o popup de edição **e** a aba Mão de Obra → os dois ficam sincronizados (corrige o bug de dessincronia).
- **Popover dinâmico** compõe peça + M.O. e fecha com o valor da linha; **toggle convergente** controla os dois filtros (peça+serviço) sem dessincronizar.
- **Honestidade técnica:** a fragilidade do intervalo foi documentada na própria tarefa e na ADR-014 em vez de varrida para baixo do tapete.

### 🔴 Bloqueante
Nenhum. `tsc` 0, `lint` 0, **272 testes** verdes; critérios de aceite cumpridos.

### 🟡 Importante
**1. Interações novas de UI sem teste de render**
- Onde: `components/mao-de-obra/CardServico.tsx` (toggle por-item), `components/detalhamento/PopoverDetalhesPeca.tsx` (composição), `components/detalhamento/CardTotalAnual.tsx` + `DialogEdicaoCusto.tsx` (chip → popup de modo).
- Problema: a infra de render-test (jsdom) existe e o smoke cobre só o render base; o comportamento do toggle (read-only `~` vs editável), a tabela de composição e o popup do chip não têm rede de proteção. Lógica de UI nova sem teste é risco de regressão silenciosa (módulo 15/21).
- Tarefa gerada: **TASK-TEST-003** (pendentes).

**2. Unificação do intervalo peça↔serviço é implícita/frágil**
- Onde: `utils/calculos.ts` (`resolverServicoComIntervaloEditado` + merge em `normalizarPerfilMvp`).
- Problema: peça e M.O. só amortizam no mesmo intervalo porque o default global (`SERVICOS_INDEPENDENTES_PADRAO`) está **defasado** em relação ao preset — é isso que faz `resolverServicoComIntervaloEditado` adotar o intervalo sincronizado também para a peça. "Corrigir" o default para casar com o preset quebraria a unificação (peça voltaria a usar `intervaloKmEntrega`/`vidaUtilKm`, ≠ serviço). Não há teste travando essa relação.
- Registrada como: **DT-19** (`docs/dominio/divida-tecnica.md`), com gatilho.

### 🟢 Sugestão
- Toggle por-item fica **escondido quando o global está ligado** (mostra "ligada em Preferências"): não dá para *desligar* a estimativa de um item específico mantendo o global. O humano já cogitou querer isso; se confirmar, inverter a precedência (per-item vence o global).
- Excepcionais (modo `independente`) não expõem o toggle por-item, embora o cálculo já suporte `estimativaMaoDeObraPorServico` para eles (`calcularImprevistosSugeridosAnual`).
- Tabelas do `PopoverDetalhesPeca` sem `scope`/`caption` (a11y leve).
- `montarEstimativaMaoDeObra` recomputa `obterPreset` + `estimarMaoDeObra` a cada render no dialog/aba — custo desprezível hoje; memoizar só se virar gargalo.
