- **Observações:** Gerada em revisão de TASK-BG-001. Bug confirmado: preço Original editado para 80, ao trocar para Paralela e voltar para Original, o valor 80 era perdido (revertia para 82 do preset). Causa raiz: `precoEditado` é campo único sem memória de qual perfil o originou. Solução de UI acordada com o usuário: substituir o toggle + input único por dois inputs simultâneos (Original e Paralela), com vida útil em km como texto informativo no card. Adicionalmente: div "vida útil" mais fino que o Input (fix de altura) e botões Segmentado em PaginaAjustes ainda finos (fix de `h-12`).

### Nova UI do CardItemPreco

O grid `grid-cols-2` já existe no card atual:
- Col 1 (esquerda): era "Preço (R$)" — vira **Original (R$)**
- Col 2 (direita): era o `div` read-only de "Vida útil" — vira **Paralela (R$)**
- "Vida útil: X km" desce para uma linha de texto abaixo do grid (full-width)

```
┌────────────────────────────────────────┐
│  Filtro de ar (tipo viscoso)  [reset]  │
│                                        │
│  Original (R$)    Paralela (R$)        │
│  ┌──────────┐    ┌──────────┐          │
│  │  82,00   │    │  29,00  │          │
│  └──────────┘    └──────────┘          │
```

Sem toggle. Dois inputs sempre visíveis e editáveis. O perfil global (Ajustes → Preferências de Manutenção) continua determinando qual preço vai para o cálculo de custo.

### Causa raiz (registro)

`PecaOverride.precoEditado` era um único `number | null` sem vínculo a um perfil. O código apagava o campo ao trocar de perfil para evitar contaminação cruzada — mas isso jogava fora a edição do usuário. Com dois inputs simultâneos, o problema de "qual perfil estava ativo" desaparece: cada campo é sempre do seu perfil.

## Decisões Tomadas

- **Dois inputs simultâneos em vez de toggle:** Elimina o problema de qual perfil estava ativo ao salvar. Com campos independentes, cada input nunca "contamina" o outro.
- **`perfilPecasOverride` removido:** Com dois inputs simultâneos, o override de perfil por peça torna-se redundante. O perfil global (`perfilManutencao.perfilPecasGlobal`) já determina qual preço entra no cálculo. Menos estado, menos fonte de bug.
- **Vida útil como `<p>` em vez de coluna:** Libera a segunda coluna do grid para o input de Paralela, sem alterar o layout existente. A informação permanece visível e sem altura mínima conflitando com o Input ao lado.

---

## O Que NÃO Foi Feito (e Por Quê)

- **Migração de localStorage:** Dados existentes com campo `precoEditado` são silenciosamente ignorados na próxima carga. Overrides de preço no ambiente de dev são perdidos. Aceito: ambiente de dev não tem dados de produção; custo de uma migration supera o benefício neste momento.
- **Revisão de UI no browser:** Sem servidor de dev rodando na sessão — revisão visual não foi feita. A estrutura de componente e os estilos seguem o padrão estabelecido nos demais cards da tela.

## Aprendizados Para o Projeto

- **Campos de override com semântica única evitam perda de estado:** `precoEditado` sem vínculo de perfil forçava o código a escolher entre "salvar e contaminar" ou "apagar e perder". Campos separados eliminam a escolha.
- **Toggle de perfil em UI = estado escondido:** Qualquer toggle que determina qual valor vai para o cálculo é uma fonte de confusão para o usuário e complexidade para o código. Preferir mostrar todos os valores simultaneamente quando possível.
