# ADR-011: Preset como fonte única de catálogo e manutenção

**Data:** 02/06/26
**Status:** Aceita
**Decisores:** Thiago (humano), IA (Codex)

## Contexto

A REV-001 identificou dois achados bloqueantes na evolução do projeto para múltiplos modelos de moto:

- **REV-001-A01:** o catálogo de modelos ainda é montado manualmente em `src/data/catalogoModelos.ts`, duplicando campos que já vivem no preset JSON e mantendo `nomeFipe`/`aceitaEtanol` apenas no TypeScript.
- **REV-001-A02:** manutenção, peças e histórico continuam acoplados à Pop 110i em defaults, tipos, schema, mapas de cálculo e nomes de UI.

O requisito não funcional RNF-10 diz que adicionar um modelo deve significar inserir um novo JSON, com zero alteração no código. O estado atual não cumpre isso: além do JSON, ainda é necessário editar catálogo, defaults e mapas.

TASK-REF-31 cria a fundação de preset/modelo como fonte única para catálogo. TASK-REF-32 depende dessa fundação para migrar manutenção, serviços, histórico e vínculos peça/serviço para dados orientados pelo preset. A decisão precisa ser tomada antes da migração em massa porque reverter depois afetaria persistência, cálculo e onboarding.

## Decisão

Adotar o **preset JSON do modelo** como fonte única dos dados estáticos do modelo.

Na primeira etapa, TASK-REF-31:

- centraliza o carregamento em `src/data/repositorioPresets.ts`;
- deriva `CATALOGO` a partir dos JSONs;
- move metadados de catálogo para o preset (`nomeFipe`, `aceitaEtanol`, além dos campos já presentes como consumo, FIPE e tabela);
- mantém `src/data/catalogoModelos.ts` como fachada compatível para reduzir o impacto imediato.

Na segunda etapa, TASK-REF-32.x:

- move defaults de serviços independentes para o preset;
- transforma histórico de últimas trocas em estrutura orientada por id do preset (`Record<string, number>` ou equivalente);
- move vínculos peça↔serviço↔histórico para o preset;
- substitui constantes específicas Honda/Pop por valores derivados do preset, incluindo o ciclo da revisão autorizada;
- renomeia vazamentos de marca na UI, preservando o vocabulário genérico "autorizada" e "independente".

### Adendo - ADR-012

Após a aceitação desta ADR, o escopo da TASK-REF-32.x foi restringido para o MVP pela [ADR-012](./ADR-012.md).

A decisão de **preset como fonte única** permanece válida. O que muda é a ordem e o escopo de execução:

- revisão independente deixa de ser requisito do MVP e fica preservada como capacidade futura;
- preços de peças paralelas ficam preservados no modelo/preset, mas escondidos da UI do MVP;
- a UI deve usar vocabulário de `Concessionária` em vez de expor `Honda` como termo genérico;
- mão de obra não informada não deve ser inferida nem somada como `R$ 0` silencioso;
- presets novos podem nascer com revisão autorizada/concessionária, preços originais e avulsos documentados, sem dados completos de oficina independente.

## Consequências

### Positivas

- Adicionar modelo passa a ser operação de dados, não edição espalhada de TypeScript.
- Catálogo, onboarding, custos e telas passam a compartilhar a mesma fonte de verdade.
- TASK-RNF-013 pode validar um contrato único de preset com Zod.
- TASK-REF-32 pode migrar manutenção sem reabrir a decisão de onde os dados do modelo vivem.

### Trade-offs Aceitos

- O preset JSON fica mais denso: além de peças e revisões, passa a conter metadados e, futuramente, relações de manutenção.
- Enquanto TASK-RNF-013 não for concluída, o carregamento ainda depende de cast para `PresetMoto`; mitigação temporária por teste de contrato.
- Manter `catalogoModelos.ts` como fachada preserva compatibilidade, mas cria uma camada intermediária que deve ser entendida como API derivada, não fonte canônica.
- TASK-REF-32 exigirá mudança em dados persistidos (`KmUltimaTrocas`), schema e cálculo; por isso será subdividida.

## Alternativas Descartadas

### Alternativa 1: Manter catálogo TypeScript manual e só corrigir duplicações pontuais

**Por que descartada:**
- Continua exigindo alteração de código para adicionar moto.
- Mantém duas fontes de verdade para metadados de modelo.
- Não resolve o achado REV-001-A01.

### Alternativa 2: Criar vários repositórios pequenos por tela

**Por que descartada:**
- Repetiria o problema atual de vários consumidores fazendo `import.meta.glob`.
- Aumenta o risco de cada tela derivar ids e metadados de forma diferente.
- Dificulta validação única em TASK-RNF-013.

### Alternativa 3: Resolver manutenção primeiro, sem repositório único de presets

**Por que descartada:**
- TASK-REF-32 depende de uma fonte confiável de preset por modelo.
- A migração de manutenção ficaria acoplada aos mesmos globs espalhados que a TASK-REF-31 pretende remover.
- A chance de refazer a fundação depois seria alta.

### Alternativa 4: Mover tudo de uma vez na TASK-REF-31

**Por que descartada:**
- O escopo atravessaria catálogo, manutenção, schema, persistência, UI e cálculo em uma única tarefa.
- TASK-REF-32 já está classificada como XG/XG, com divisão obrigatória pelo protocolo.
- O risco de quebrar comportamento testado em `calculos.ts` seria desnecessariamente alto.
