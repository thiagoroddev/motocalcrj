# ADR-015: FIPE hardcoded por preset + atualização mensal por script (BrasilAPI runtime aposentada)

**Data:** 04/06/26
**Status:** Aceita
**Decisores:** Thiago (humano), IA (Claude)

## Contexto

O valor venal (FIPE) é usado para estimar o IPVA (`calcularIPVA(valorFipe, aliquota, ...)`). Até aqui o fluxo era:

- No onboarding **Passo 3**, o app consultava a **BrasilAPI FIPE** em runtime (`src/services/fipeService.ts`) para obter o valor do ano informado, com a `tabelaFipe` hardcoded do preset como **fallback offline** (rotulado "estimativa").
- A `tabelaFipe` (ano → valor) já existe em cada preset e é validada por schema (TASK-RNF-013).

Dois problemas tornaram o lookup runtime indesejável:

1. **A BrasilAPI provou-se instável:** na TASK-CHORE-017 ela respondeu **HTTP 500** por erro upstream 403 da FIPE. É uma dependência externa **no caminho crítico do onboarding**.
2. **Não há necessidade de tempo real:** a FIPE tem referência **mensal** e muda devagar; um estimador de custo não precisa do valor ao vivo.

A TASK-CHORE-017 entregou um **script mensal** (`npm run fipe:update`) que atualiza a `tabelaFipe` e o `codigoFipe` dos presets, commitados no repositório. Ele consulta a **API REST da Parallelum FIPE** (`https://parallelum.com.br/fipe/api/v2`), documentada no repositório [`parallelum/fipe-go`](https://github.com/parallelum/fipe-go). Optou-se por chamar a REST direto (não o SDK Go) para não introduzir Go no toolchain TS/Vite.

## Decisão

1. **A `preset.tabelaFipe[ano]` passa a ser a fonte ÚNICA do valor FIPE** no app — sem chamada de API em runtime. O onboarding lê o valor de forma **síncrona** do catálogo/preset.
2. **A BrasilAPI runtime é aposentada:** `src/services/fipeService.ts` (e seu teste) são removidos; o Passo 3 deixa de fazer fetch/debounce e de exibir o estado "estimativa (FIPE offline)".
3. **Atualização é mensal e versionada:** roda-se `npm run fipe:update` (CHORE-017), revisa-se o diff e commita-se. O valor do app é "FIPE da última atualização".
4. **`fipeCache` é mantido** como o snapshot persistido do valor escolhido (agora vindo da `tabelaFipe`), para **não tocar `calculos.ts`** (gated): `calcularCustosPorCategoria` continua lendo `perfil.fipeCache?.valor`.
5. **Ano fora da `tabelaFipe`** → o app mostra "valor indisponível" e o IPVA é tratado como o fluxo já trata ausência (não há lookup ao vivo para preencher a lacuna).

## Consequências

### Positivas
- **Onboarding offline-first:** zero dependência de rede no caminho crítico; sem flakiness de API externa.
- **Determinístico e testável:** o valor é dado de build, validado por schema (RNF-013); o smoke de onboarding fica mais simples e rápido (sem mock de fetch).
- **Passo 3 mais simples:** sem estados `buscando`/`fallback`, sem debounce, sem cache de 30 dias para evitar re-fetch.

### Trade-offs Aceitos
- O valor FIPE é o **da última rodada do script** (mensal), não tempo real — aceitável para o domínio.
- Exige **disciplina mensal** (rodar o script + commitar). Mitigação possível: GitHub Action manual/scheduled abrindo PR com o diff (sugerido na revisão da CHORE-017).
- Modelo/ano **não presente** na `tabelaFipe` não tem valor — cobre-se ampliando a tabela no preset (o script já traz o range completo por código FIPE).

## Alternativas Descartadas
- **Manter a BrasilAPI e endurecer o parsing (TASK-RNF-014):** rejeitada — não faz sentido blindar uma API instável que sai do caminho. A RNF-014 foi **cancelada** por esta decisão.
- **Proxy/cache server próprio para a FIPE:** over-engineering para um app local-first pré-lançamento.
- **Remover `fipeCache` e ler `tabelaFipe` direto no cálculo:** descartada no escopo da REF-36 por tocar `calculos.ts` (gated) + migração de schema; pode ser reavaliada no futuro.

- **Cancela:** TASK-RNF-014 (validar BrasilAPI) — ver `concluidas/2026-06-04--18h35--TASK-RNF-014-CANCELADA.md`.
- **Afeta:** `src/pages/onboarding/passos/Passo3.tsx`, `src/services/fipeService.ts` (removido), docs (glossário "BrasilAPI / FIPE" e "FIPE Cache", requisitos).
