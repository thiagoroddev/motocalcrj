# ADR-008: Tokens de spacing seguem a escala numérica padrão do Tailwind/shadcn

**Data:** 30/05/26
**Status:** Aceita
**Decisores:** Thiago (humano), IA (Claude)

---

## Contexto

O `@theme` em `src/index.css` redefinia o namespace de spacing com chaves nomeadas:

```css
--spacing-xs: 4px;
--spacing-sm: 8px;
--spacing-md: 16px;
--spacing-lg: 24px;
--spacing-xl: 32px;
```

No **Tailwind v4**, definir `--spacing-<chave>` faz qualquer utility que resolva por essa chave passar a usar o valor de spacing. As chaves `sm/md/lg/xl` são **compartilhadas** com a escala de container que `max-w-*` consome. Resultado, confirmado no CSS compilado:

| classe | compilava como | valor padrão correto |
|---|---|---|
| `max-w-sm` | 8px | 24rem |
| `max-w-md` | 16px | 28rem |
| `max-w-lg` | **24px** | 32rem |
| `max-w-xl` | 32px | 36rem |

Foi a **causa-raiz da TASK-BG-009**: o `DialogContent` (`sm:max-w-lg`) colapsava para 24px em telas ≥640px — os pop-ups viravam uma tira vertical. A BG-009 aplicou um paliativo (valores arbitrários `max-w-[32rem]` nos 3 modais), mas o "landmine" permanecia: qualquer `max-w-lg`/`max-w-sm` futuro nasceria quebrado.

Tentativas de corrigir sem remover o namespace **não funcionam**: redefinir `--container-lg` no `@theme` não tem efeito — o `--spacing-lg` nomeado continua vencendo na resolução de `max-w-lg`.

## Decisão

**Eliminar o namespace `--spacing-*` customizado.** O app passa a usar a **escala numérica padrão do Tailwind/shadcn** (`p-4`, `gap-2`, `space-y-4`, …). Tailwind e shadcn voltam a ditar os tokens de spacing/sizing.

Conversão 1:1 (px idênticos — sem mudança visual):

| token removido | px | canônico |
|---|---|---|
| `xs` | 4 | `1` |
| `sm` | 8 | `2` |
| `md` | 16 | `4` |
| `lg` | 24 | `6` |
| `xl` | 32 | `8` |

168 utilities convertidas em 44 arquivos. Os 3 modais da BG-009 revertidos aos canônicos (`max-w-lg`/`max-w-sm`/`max-w-xl`), que agora resolvem corretamente.

### Guard-rail (impede regressão)

`scripts/check-spacing-tokens.mjs` (zero dependências) falha o `npm run lint` se encontrar:
1. utility de spacing (`p`/`m`/`gap`/`space`/`scroll-*`) com sufixo nomeado `xs/sm/md/lg/xl`;
2. redefinição de `--spacing-<chave-nomeada>` em CSS.

O script **não** bloqueia `max-w-lg`, `min-h-touch` etc. — sizing/position usam a escala de container e aceitam chaves nomeadas legitimamente.

## Consequências

### Positivas

- **Causa-raiz eliminada:** `max-w-*` (e qualquer utility que use a escala de container) volta a funcionar para sempre.
- **Maximiza consistência no desenvolvimento com IA:** o código usa a escala que o modelo já conhece por padrão (`p-4`, `gap-2`). O *prior* da IA fica sempre correto — sem convenção local para "lembrar" a cada arquivo, que era justamente a fonte da deriva.
- **Menos uma camada de indireção:** quem lê `p-4` sabe o valor sem consultar tabela de tokens.
- **Guard-rail automatizado:** a regra deixa de depender de disciplina humana/IA e passa a ser barrada no CI.

### Trade-offs Aceitos

- **Perde a legibilidade semântica** de `p-md`/`gap-lg` ("spacing médio/grande"). Para um time humano grande com design system maduro, tokens semânticos seriam defensáveis — mas viveriam num namespace que **não colide** (ex.: `--space-*`) e com documentação rigorosa. Para um projeto fortemente assistido por IA, esse ganho semântico é exatamente o que causa a deriva; a escala padrão vence.
- **Alto churn pontual** (44 arquivos), mas 1:1 em px → sem mudança de layout. Mitigado por: conversão determinística + guard-rail (0 remanescentes) + suíte de testes verde.

## Alternativas Descartadas

### 1. Valores arbitrários nos modais (paliativo da BG-009)
`max-w-[32rem]` resolve o sintoma, mas mantém o namespace colidente — qualquer `max-w-lg` futuro nasce quebrado. É contornar, não corrigir.

### 2. Renomear `--spacing-*` para chaves próprias não-colidentes (ex.: `--spacing-1`… ou `--space-*`)
Mantém tokens customizados. Continua sendo uma convenção local que foge do padrão que o framework e a IA esperam — contraria o objetivo de maximizar consistência com IA.

### 3. Redefinir `--container-*` no `@theme`
Testado: não tem efeito. O `--spacing-*` nomeado vence na resolução de `max-w-*`.
